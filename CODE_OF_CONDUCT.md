# Code of conduct

## The short version

Be decent. Assume good faith. Technical disagreements are welcome; personal ones
are not.

## What that means here

**Criticise the code, not the person.** "This will leak an assertion if the
service throws" is a good review comment. "Did you even test this" is not, and
it is also less useful, because it does not say what to look at.

**Assume the other person knows something you do not.** This project exists
because a commercial remote-desktop tool was audited rather than dismissed:
finding out *where* it stops was what shaped the design. The same applies to
people.

**Say when you are unsure.** "I could not verify this on Linux" and "I think
this is right but the type system disagrees" are valuable contributions, not
admissions. The repository is full of notes recording what was *not* verified,
on purpose — that is the house style, not a fallback.

**Do not be a jerk about platforms, tools or skill levels.** This project
involves macOS power management, Linux networking, Android packaging and
TypeScript type-level trickery. Nobody is expected to know all of it.

## Scope

This applies to issues, pull requests, commit messages, and any project space.
It also applies to how you talk about other projects: the comparison to
commercial tools in the documentation is deliberately factual, and should stay
that way.

## Enforcement

Report a problem to the maintainers through GitHub, or privately via the contact
route in [SECURITY.md](SECURITY.md) if you would rather not say it in public.

Maintainers may edit or remove comments, close issues, or block accounts. The
response will be proportionate and explained, because an unexplained moderation
action is its own kind of rudeness.

## Attribution

This is not the Contributor Covenant, though it is compatible with it. It is
short on purpose: a code of conduct that people actually read is worth more than
a thorough one they scroll past, and this project's conventions lean towards
saying a thing plainly once.
